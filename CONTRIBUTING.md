# Участие в разработке «Мультифоры»

Спасибо за интерес к проекту **«Мультифора»**! Это Windows-приложение для пакетной работы с файлами: переименования, конвертации, объединения и сжатия. Помочь проекту можно не только кодом, но и сообщениями об ошибках, тестированием, предложениями улучшений и правками документации.

Репозиторий: <https://github.com/VseMirka200/multifora>  
Документация: <https://vsemirka200.github.io/multifora/>

Перед участием ознакомьтесь с [Кодексом поведения](CODE_OF_CONDUCT.md), [политикой безопасности](SECURITY.md) и [правилами поддержки](SUPPORT.md).

## Как помочь проекту

- **Сообщить об ошибке:** выберите подходящий [шаблон GitHub Issues](https://github.com/VseMirka200/multifora/issues/new/choose). Есть отдельные шаблоны для общих ошибок, проблем обработки файлов и интерфейса.
- **Предложить функцию:** используйте шаблон «Предложение функции» и опишите задачу, пример использования и ожидаемое поведение.
- **Помочь другим пользователям:** участвуйте в [GitHub Discussions](https://github.com/VseMirka200/multifora/discussions), если раздел доступен вашему аккаунту.
- **Улучшить код или документацию:** сначала посмотрите открытые Issues и согласуйте крупные изменения с сопровождающими проекта.

**Важно:** не публикуйте подробности уязвимостей в Issues, Discussions или Pull Requests. Для них предусмотрен [конфиденциальный канал](SECURITY.md#как-сообщить-об-уязвимости).

## Перед началом работы

1. Проверьте, нет ли уже открытого обращения с похожей проблемой или предложением.
2. Для существенных изменений сначала обсудите предполагаемое решение в Issue или Discussion. Это не гарантирует принятия изменения, но помогает избежать лишней работы.
3. Работайте с одной задачей за раз. Не объединяйте исправление ошибки с несвязанным рефакторингом.
4. Используйте **тестовые файлы или копии**, а не оригиналы важных документов. Не включайте реальные пользовательские документы в тесты или коммиты.

Pull Requests в репозитории включены, а ветка `main` защищена обязательными проверками. При этом политика создания PR может ограничивать доступ внешних участников: если кнопка создания PR недоступна, сначала предложите изменение в [Issues](https://github.com/VseMirka200/multifora/issues/new/choose) или [Discussions](https://github.com/VseMirka200/multifora/discussions).

## Среда разработки

Рекомендуемая и используемая в CI среда:

- **Операционная система:** Windows x64.
- **Python:** 3.11 x64.
- **Интерфейс:** PySide6 (Qt).
- **Управление зависимостями:** файлы `requirements.txt`, `requirements-runtime.txt`, `requirements-dev.txt`, `requirements-build.txt` с зафиксированными версиями.
- **Проверки:** `pytest`, `ruff`, GitHub Actions.

### Установка и запуск из исходников

Откройте PowerShell и выполните:

```powershell
git clone https://github.com/VseMirka200/multifora.git
cd multifora
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe multifora_start.py
```

`requirements.txt` включает зависимости для работы приложения, разработки и Windows-сборки. Для конвертации части документов при запуске из исходников может потребоваться [Pandoc](https://pandoc.org/installing.html). Приложение ищет `pandoc.exe` в `bin\pandoc`, в `PATH` или по пути из `MULTIFORA_PANDOC_PATH`. Экспорт в PDF через Pandoc также требует TeX-движок; его путь при необходимости задаётся переменной `MULTIFORA_PANDOC_PDF_ENGINE`. Для некоторых офисных преобразований может потребоваться Microsoft Word. Старый бинарный формат DOC не поддерживается: используйте DOCX.

См. также [README — Разработка](README.md#разработка) и [инструкцию по установке](https://vsemirka200.github.io/multifora/guide/install.html).

## Организация исходного кода

| Путь | Назначение |
| --- | --- |
| `app/` | Код приложения и интерфейса. |
| `core/` | Общие компоненты обработки и вспомогательная логика. |
| `multifora_start.py` | Точка входа при запуске из исходников. |
| `tests/` | Автоматические тесты. |
| `scripts/` | Скрипты проверки окружения, сборки, установщика и публикации. |

| `assets/` | Ресурсы приложения. |

Перед изменением кода найдите существующие функции и тесты, относящиеся к нужному действию. Не создавайте параллельную реализацию, если можно безопасно улучшить существующую.

## Правила изменений

- Следуйте существующему стилю кода и настройкам `pyproject.toml`: Python 3.11, правила Ruff, предельная длина строки — **120 символов**.
- Сохраняйте текстовые файлы в **UTF-8 без BOM** с окончанием строк **LF** согласно `.editorconfig` и проверкам репозитория.
- Пишите понятные комментарии и сообщения об ошибках. Не изменяйте пользовательские тексты без необходимости.
- Для исправления ошибки по возможности добавляйте регрессионный тест. Для новой функции — тесты ожидаемого и ошибочного поведения.
- При изменении интерфейса проверьте обе темы оформления, доступность элементов, масштабирование и ситуации с длинными названиями файлов.
- При изменении обработки файлов проверяйте коллизии имён, отсутствие прав, заблокированные файлы, неверные и повреждённые данные, пути с пробелами и кириллицей, отмену операции и сохранность оригиналов.
- При изменении запуска внешних программ, обновления, путей и работы с архивами учитывайте безопасность входных данных и не используйте небезопасное формирование команд.
- Не коммитьте виртуальные окружения, каталоги `build/`, `dist/`, кэши, журналы, личные настройки, секреты и пользовательские документы. Сверяйтесь с `.gitignore`.
- Если изменилось поведение для пользователей, обновите соответствующие разделы `README.md`, документации или `CHANGELOG.md`.

## Проверка изменений

Запускайте команды **из корня репозитория** в PowerShell:

```powershell
$env:QT_QPA_PLATFORM = "offscreen"
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe scripts/verify_build_environment.py
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m pytest -q
```

Для отладки одного сценария можно запустить конкретный тест:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_rename_validation.py
```

Если меняли работу файлов, дополнительно проверьте вручную соответствующую операцию на **копиях** небольшого набора файлов. Запуск `pytest` и `ruff` не заменяет проверки готовой Windows-сборки, если затронуты упаковка, установка, системная интеграция или запуск.

В CI выполняются проверки в Windows, включая установку зависимостей, `pip check`, `verify_build_environment.py`, `ruff check` и `pytest`. В отдельных workflow также проверяются сборка Windows, зависимости и безопасность.

## Изменения зависимостей

Зависимости зафиксированы в файлах `requirements-*.txt`. Не обновляйте версии без причины и не заменяйте точные версии плавающими ограничениями без согласования. При обновлении:

1. Объясните, зачем нужна зависимость или новая версия.
2. Проверьте происхождение пакета, лицензию и риски безопасности.
3. Согласованно обновите нужные файлы зависимостей и при необходимости документацию.
4. Выполните `pip check`, проверку окружения, линтер, тесты и, если изменение влияет на поставляемые библиотеки, сборку приложения.

## Подготовка Pull Request

Изменения в защищённую ветку `main` предлагаются через Pull Request. Перед слиянием должны успешно пройти обязательные проверки: качество кода в Windows, аудит зависимостей и CodeQL для Python. Автоматическое слияние обновлений Dependabot временно отключено: перед принятием таких изменений необходима ручная проверка.

Когда создание Pull Requests доступно, используйте следующую последовательность:

1. Создайте отдельную ветку от актуальной `main` с понятным названием, например `fix/rename-collision` или `docs/install-guide`.
2. Вносите небольшие логически связанные изменения. Не добавляйте автосгенерированные сборки, персональные файлы и секреты.
3. Проверьте изменение локально, добавьте тесты и при необходимости обновите документацию.
4. Подготовьте понятное описание: **что изменено**, **зачем**, **как проверено**, ссылка на Issue и снимки экрана для изменений интерфейса.
5. Заполните существующий [шаблон PR](.github/pull_request_template.md) и ответьте на замечания при проверке.

Рекомендуемые сообщения коммитов: `fix: исправить конфликт имён при переименовании`, `docs: уточнить установку`, `test: добавить проверку конвертации`. Это примеры, а не обязательный формат.

Решение о принятии и сроках рассмотрения изменений остаётся за сопровождающими. Сложные изменения могут потребовать переработки или быть отклонены с объяснением.

## Выпуск версии

Этот раздел предназначен прежде всего для сопровождающих проекта. Выпуск должен выполняться из доверенного кода после проверки изменений.

1. Определите версию приложения в `app/core/app_identity.py` (`APP_VERSION`) и обновите [журнал изменений](CHANGELOG.md) при необходимости.
2. Проверьте совместимость зависимостей, документацию и результаты CI. Тег выпуска должен соответствовать версии приложения в формате `v<версия>`, например `v1.0.3` для `APP_VERSION = "1.0.3"`.
3. При необходимости локально проверьте сборку в Windows. Скрипт `scripts\build_app.bat --no-pause` собирает `dist\Multifora\Multifora.exe`. Для установщика нужен **Inno Setup 6**; после сборки приложения используйте `scripts\build_installer.bat --skip-app-build`.
4. Для проверок сборки предусмотрены `scripts\verify_windows_runtime.ps1`, `scripts\verify_installer.ps1` и сценарии упаковки в `scripts/`. Перед распространением проверьте установку, запуск и работу на тестовых файлах.
5. Workflow [«Выпуск версии»](.github/workflows/release.yml) запускается **только при отправке тега `v*`**. Тег должен соответствовать `APP_VERSION`. Workflow собирает Windows-приложение и установщик, формирует портативный ZIP и контрольные суммы SHA-256, затем публикует **новый** GitHub Release. Существующие релизы и их файлы автоматически не перезаписываются.
6. Проверьте [опубликованный выпуск](https://github.com/VseMirka200/multifora/releases) и файлы установщика, портативной версии и контрольных сумм. Если автоматическая публикация завершилась ошибкой, выясните причину, прежде чем повторять процесс.

**Не создавайте релизы из непроверенных веток или кода неизвестного происхождения.** Не передавайте третьим лицам токены публикации и секреты CI.
