Спасибо за интерес к Мультифоре. Принимаются исправления ошибок, тесты, улучшения интерфейса и документации, а также заранее обсуждённые функции.

## Среда разработки

Основная среда разработки — Windows и Python 3.11 x64. Все Windows-workflow проекта используют Python 3.11; совместимость с другими версиями проверяйте отдельно.

```powershell
git clone https://github.com/VseMirka200/multifora.git
cd multifora
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe multifora_start.py
```

Microsoft Word требуется только для части операций с документами. Ghostscript поставляется с готовой Windows-сборкой и используется для сжатия PDF; при его недоступности предусмотрена обработка через PyMuPDF.

Интерфейс использует PySide6 (Qt for Python). После обновления исходников установите зависимости заново командой `python -m pip install -r requirements.txt` из активированного окружения. В Windows-сборку включается только PySide6; другие привязки Qt исключены в `Multifora.spec`.

## Как предложить изменение

1. Создайте ветку от актуальной `main`.
2. Ограничьте Pull Request одной понятной задачей.
3. При изменении поведения добавьте или обновите соответствующий тест.
4. Запустите проверки:

   ```powershell
   $env:QT_QPA_PLATFORM = "offscreen"
   .\.venv\Scripts\python.exe -m pytest -q
   .\.venv\Scripts\python.exe -m ruff check .
   ```

5. В Pull Request опишите проблему, решение, способ проверки и известные ограничения. Для заметных изменений интерфейса приложите снимки экрана.

Не добавляйте в коммиты виртуальные окружения, сборки, кэши, журналы, токены, ключи, личные данные или пользовательские документы.

Предлагайте изменения в `main` через Pull Request. Для PR настроены проверки качества, аудит зависимостей, CodeQL и сборка Windows-приложения с установщиком. Правила обязательного прохождения проверок задаются отдельно в настройках GitHub.

## Структура проекта

- `app/` — интерфейс PySide6, настройки и модели приложения.
- `core/` — фоновые операции над файлами, конвертация, сжатие и объединение.
- `tests/` — автоматические проверки поведения и файловых операций.
- `scripts/` — сборка и проверка Windows-пакета и установщика.
- `docs/` — сайт руководства; правила участия и политики проекта находятся в корне репозитория.

Проверяйте изменения файловых операций на временных копиях: сохранность содержимого, конфликты имён, отмену и повтор. Для исправления только текста или оформления достаточно соответствующей ручной проверки; тесты нужны для нового или изменённого поведения.

## Локальная сборка

Из корня репозитория:

```powershell
.\scripts\build_app.bat --no-pause
.\scripts\build_installer.bat --skip-app-build
.\.venv\Scripts\python.exe scripts\verify_windows_bundle.py --bundle dist\Multifora
.\scripts\package_release.ps1
```

Для установщика нужен Inno Setup 6. Готовое приложение находится в `dist/Multifora`, установщик — в `dist/installer`. Локальная упаковка создаёт `dist/Multifora-Portable-<версия>.zip` и `dist/SHA256SUMS.txt`.

Сборка использует отдельное окружение `.venv-build`, Python 3.11 x64 и точные версии всех зависимостей из [requirements.txt](requirements.txt). Для окружения разработки `.venv` также требуется Python 3.11 x64, поскольку закреплённые бинарные пакеты проверяются именно с этой версией. Скрипт проверяет версию Python до установки пакетов, затем проверяет их совместимость и совпадение с закреплёнными версиями.

Обновляйте `requirements.txt` отдельным изменением вместе с зависимостями этих пакетов. Перед принятием обновления выполните тесты, соберите EXE и запустите `./scripts/verify_windows_runtime.ps1`. Эта проверка открывает главное окно в тестовом режиме, создаёт и читает PDF, объединяет DOCX в памяти и запускает Ghostscript. Она выполняется в PR и перед публикацией релиза; ошибка останавливает выпуск. Аудит безопасности проверяет этот же закреплённый набор пакетов.

## Выпуск версии

1. Обновите `APP_VERSION` в [app/core/app_identity.py](app/core/app_identity.py) и резервную версию `MyAppVersion` в [scripts/installer.iss](scripts/installer.iss). Версия указывается без префикса `v`.
2. Опишите изменения в [CHANGELOG.md](CHANGELOG.md), выполните проверки и отправьте PR в `main`.
3. После слияния PR workflow [«Выпуск версии»](.github/workflows/release.yml) возьмёт версию из кода, запустит тесты, соберёт и опубликует выпуск. Также поддерживается запуск отправкой тега `v<версия>`; версия тега должна совпадать с кодом.
4. Проверьте опубликованные контрольные суммы, запуск переносной версии и работу установщика.

GitHub Release содержит:

- `Multifora-Setup-<версия>.exe` и одноимённый `.sha256`;
- `Multifora-Silent-Install-<версия>.bat` и одноимённый `.sha256`;
- `Multifora-v<версия>-windows-x64.zip` и `Multifora-v<версия>-windows-x64.sha256`.

Батник тихой установки запускается рядом с установщиком и может показать системный запрос прав администратора. Описание нового релиза формируется из истории коммитов; корневой `CHANGELOG.md` — отдельный журнал проекта.

Текущий workflow заменяет файлы уже существующего релиза с тем же тегом. Для нового выпуска повышайте версию: повторная публикация под прежним номером меняет файлы, которые пользователи могли уже скачать. Скрипт локальной упаковки и workflow используют разные имена ZIP-архива — учитывайте это при проверке файлов.
