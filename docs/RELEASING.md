# Подготовка выпуска

Официальные выпуски собираются workflow `.github/workflows/release.yml` при публикации тега вида `v*`.

## Перед выпуском

1. Убедитесь, что рабочая ветка содержит только запланированные изменения.
2. Обновите `APP_VERSION` в `app/core/app_identity.py`.
3. Перенесите изменения из раздела «Не выпущено» в новую версию `CHANGELOG.md` и добавьте дату.
4. Проверьте README и инструкции безопасности.
5. Запустите тесты:

```powershell
$env:QT_QPA_PLATFORM = "offscreen"
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

6. При наличии Ruff запустите `python -m ruff check .`.
7. Соберите приложение и установщик локально при изменениях упаковки:

```powershell
.\scripts\build_app.bat --no-pause
.\scripts\build_installer.bat --skip-app-build
```

## Версия и тег

Версия тега без `v` обязана совпадать с `APP_VERSION`. Пример:

```text
APP_VERSION = "0.10.0"
tag = v0.10.0
```

Несовпадение останавливает release workflow.

## Публикация

После слияния подготовленного изменения в `main` создайте и отправьте подписанный или аннотированный тег согласно правилам проекта:

```powershell
git tag -a v0.10.0 -m "Мультифора 0.10.0"
git push origin v0.10.0
```

Workflow выполняет тесты, собирает PyInstaller-каталог, создаёт Inno Setup installer, рассчитывает SHA-256 и публикует GitHub Release.

## Проверка результата

После завершения workflow проверьте:

- ZIP распаковывается и запускается;
- установщик устанавливает и обновляет приложение без потери настроек;
- опубликованы `.sha256` для ZIP и EXE;
- версия в интерфейсе совпадает с тегом;
- контекстное меню, ярлыки и проверка обновлений работают;
- заметки выпуска понятны пользователю.

Если проверка не пройдена, удалите ошибочный релиз и тег только после анализа причины и подготовьте новый patch-релиз. Не заменяйте незаметно уже опубликованные бинарные файлы под тем же тегом.
